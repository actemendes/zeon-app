# Аудит безопасности Android-приложения ZEON

Дата: 18 июля 2026 г.

## Цель и модель угроз

Основная цель — исключить получение JWT, ссылок подключения, конфигураций и иных токенов через обычный ADB с не-rooted устройства, не ломая подключение VPN, импорт профилей, уведомления и обновление существующих профилей.

Важно: установленное на контролируемое злоумышленником устройство клиентское приложение не может хранить вечный общий API-ключ как настоящий секрет. Значение, необходимое приложению для запроса, можно извлечь из APK, памяти процесса или перехватить с помощью root/hooking. Клиентское усиление защищает данные в покое и от обычного ADB; окончательная защита сервиса должна обеспечиваться авторизацией и ограничениями на сервере.

## Результат

| Сценарий | После исправлений |
| --- | --- |
| Обычный ADB + production APK | Sandbox недоступен через `run-as`; backup отключён; чувствительные рабочие файлы не лежат во внешнем хранилище; release-logcat приложения отключён |
| Анализ APK | JWT пользователя отсутствует; общий мобильный API-ключ и встроенный bootstrap всё ещё технически извлекаемы |
| Root, Frida/hooking, дамп памяти | Активный JWT и расшифрованная конфигурация могут быть получены; риск снижается только коротким TTL, ротацией и серверным контролем |
| Потерянное разблокированное устройство | Токены в покое защищены Android Keystore/EncryptedSharedPreferences и внутренним sandbox, но активная сессия остаётся риском до серверного отзыва |

## Критичные находки до исправлений

1. На подключённом тестовом устройстве установлен пакет с флагами `DEBUGGABLE` и `ALLOW_BACKUP`. Команда `run-as` выполнялась успешно. Чтение внутренних данных не проводилось.
2. JWT устройства и ссылка подключения сохранялись в обычных SharedPreferences.
3. Рабочий каталог находился в `/sdcard/Android/data/.../files`. Обычный ADB подтверждал право чтения журнала, базы ядра и незашифрованного runtime-конфига. Содержимое файлов во время аудита не читалось.
4. Общий мобильный API-ключ встроен в Dart-клиент и присутствует в истории Git. Его необходимо считать скомпрометированным независимо от обфускации.
5. В журнал попадали полные ссылки подключения, значения настроек, ответы API, WARP-данные, идентификаторы и сведения о профиле. Release-приложение также писало в logcat.
6. Release-сборка могла молча использовать debug-сертификат при отсутствии production keystore.
7. Метаданные профиля в Android-базе не проходили через уже существующий слой защиты, хотя сами файлы профилей шифровались AES-256-GCM.

## Выполненные исправления

- JWT устройства и connection link перенесены в `flutter_secure_storage` с Android EncryptedSharedPreferences/AES-GCM. Добавлена ленивая миграция старых значений без plaintext fallback для новых секретов.
- Android working directory перенесён во внутренний app-private каталог. Старые конфиги, база и журналы копируются до запуска ядра, проверяются и удаляются из внешнего каталога только после успешного переноса. При ошибке сохраняется старый путь, чтобы не потерять профиль, а миграция повторяется при следующем запуске.
- Защита чувствительных полей профиля включена для Android.
- Добавлены `allowBackup=false`, правила исключения данных из cloud backup/device transfer и глобальный запрет cleartext. Исключение для локального loopback-трафика VPN-ядра сохранено.
- Release-сборка явно не-debuggable и теперь завершается ошибкой без release keystore; fallback на debug signing удалён.
- Android-скрипты установки по умолчанию собирают release и предупреждают при явном выборе debug/profile.
- Полные URI, connection link, ответы API, значения preferences, токены и данные профиля удалены из журналов. Dart-logcat отключён в Android release. Редактор диагностических отчётов распознаёт bearer/basic credentials, JWT, API-ключи, URL, proxy URI и секреты из журналов старых версий.
- Production-компиляция игнорирует developer JWT, debug bootstrap URL и debug UDP probe secret из `--dart-define`, чтобы такие значения нельзя было случайно встроить в release APK.
- Конфигурация secure storage для стабильного device ID приведена к единому защищённому режиму.

## Проверка

- 18 целевых unit-тестов прошли.
- Release APK успешно собран из `lib/main_prod.dart`.
- Итоговый APK подписан production-сертификатом по APK Signature Scheme v2.
- `apkanalyzer` подтвердил `debuggable=false`.
- Манифест APK подтвердил `allowBackup=false`, `fullBackupContent=false`, `usesCleartextTraffic=false` и наличие data-extraction/network-security rules.
- Статический анализ всех изменённых Dart-файлов завершился без замечаний.

## Обязательные серверные действия (P0)

1. Немедленно отозвать и заменить текущий общий мобильный API-ключ: он находится в исходниках, истории Git и уже выпущенных APK.
2. Считать новый клиентский API-ключ публичным идентификатором приложения, а не фактором авторизации. Он не должен давать доступ к данным пользователя или привилегированным операциям.
3. Проверять владение ресурсом только по `sub`/device identity из проверенного JWT. Не доверять переданным клиентом `user_id`, `device_id` или аналогичным идентификаторам для выбора чужих данных.
4. Выдавать устройству короткоживущий access JWT и отдельный ротируемый/revocable refresh credential; отзывать все сессии устройства при rebind/logout/подозрении.
5. Защитить первичную регистрацию одноразовым кодом/челленджем, проверкой подлинности приложения и устройства, rate limit и anti-enumeration. Проверка целостности повышает стоимость атаки, но не заменяет серверную авторизацию.
6. Сделать bootstrap-профиль уникальным или короткоживущим для устройства. Встроенный общий профиль, даже закодированный или обфусцированный, является публичным.
7. Добавить серверный аудит аномалий: массовые lookup/register/bind/rebind, повторное использование bootstrap, частые ротации и географически невозможные сессии.

## Остаточные риски и решения

- WARP access token/license/config остаются в обычных внутренних SharedPreferences. В production они закрыты sandbox и исключены из backup, но для дополнительной защиты от offline-дампа их следует перенести в secure storage отдельной задачей.
- `ShortcutActivity` экспортирована для системного ярлыка и может быть вызвана другим приложением для переключения VPN. Закрытие компонента сломает ярлык; если этот сценарий нежелателен, нужен новый UX без экспортированной toggle-activity.
- `QUERY_ALL_PACKAGES` используется для per-app VPN. Удаление разрешения повысит приватность, но потребует переработать выбор приложений и может изменить текущую функциональность.
- Пользовательские deep links остаются поверхностью импорта конфигураций. Нужно поддерживать строгую валидацию схемы/размера и подтверждение пользователя перед импортом.
- TLS pinning и Dart obfuscation могут повысить стоимость анализа, но не делают общий API-ключ секретным и требуют процесса ротации сертификатов/хранения symbol maps.
- Нельзя распространять debug/profile APK. Текущая тестовая debug-установка подписана иначе и не должна считаться проверкой production-защиты; её нельзя безопасно обновить release APK с другим сертификатом без удаления или отдельного миграционного плана.

## Критерий готовности к публикации

Клиентская часть готова против обычного ADB после установки нового release APK и успешной миграции внешнего рабочего каталога. Публиковать её как полное исправление защиты сервиса следует только после ротации текущего общего ключа и закрытия серверных сценариев, где этот ключ является самостоятельной авторизацией.
