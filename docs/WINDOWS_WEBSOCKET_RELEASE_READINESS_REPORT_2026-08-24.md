## A. WebSocket architecture

The production Windows system-network route now loads `zeon_windows_transport.dll`, a minimal C++ WinHTTP transport. The native session uses:

- `WinHttpOpen(..., WINHTTP_ACCESS_TYPE_AUTOMATIC_PROXY, ..., WINHTTP_FLAG_ASYNC)`;
- `WinHttpSetTimeouts`, `WinHttpConnect`, `WinHttpOpenRequest`, and `WINHTTP_OPTION_UPGRADE_TO_WEB_SOCKET`;
- `WinHttpSendRequest`, `WinHttpReceiveResponse`, status/header/auth queries, and `WinHttpSetCredentials`;
- `WinHttpWebSocketCompleteUpgrade`;
- `WinHttpWebSocketReceive`, `WinHttpWebSocketSend`, `WinHttpWebSocketShutdown`, `WinHttpWebSocketQueryCloseStatus`, and `WinHttpWebSocketClose`;
- `WinHttpSetStatusCallback` and `WinHttpCloseHandle`.

Proxy/PAC resolution, DNS/connect, TLS, HTTP upgrade, reads, writes, shutdown, and request errors complete through WinHTTP status callbacks. The Flutter isolate never runs a blocking receive or polling loop. A Dart worker isolate only drains a bounded native event queue with a 200 ms wait; UI-side FFI calls enqueue/start asynchronous native operations and return promptly.

Native handles follow the lifecycle `internet -> connect -> request -> websocket`. The request handle is closed after successful upgrade. Session registry ownership remains alive until Dart requests release and every context-bearing WinHTTP handle reports `HANDLE_CLOSING`.

The transport assembles text and binary fragments, preserves empty messages, limits a message to 8 MiB, limits queued event payloads to 16 MiB/128 events, and limits queued sends to 8 MiB/64 messages. Queue overflow terminates and closes the native session rather than accumulating memory indefinitely.

## B. Concurrency safety

- At most one native receive is outstanding.
- Sends are serialized through a retained-buffer queue; the buffer is released only after `WRITE_COMPLETE`.
- A send and receive may progress concurrently, as allowed by WinHTTP, without two same-direction operations sharing a handle unsafely.
- Local close waits for queued sends, performs one shutdown, has a five-second deadline, and aborts handles if bounded shutdown cannot complete.
- Remote close records close code/reason, sends protocol close, then closes all handles.
- Cancellation is thread-safe, closes request/websocket handles, wakes the event pump, and is bounded from the Flutter caller's perspective.
- Callback lookup uses a registry-owned `shared_ptr`; the session is not erased until all handle-closing callbacks finish. Late callbacks therefore cannot target freed Dart/native session memory.
- Invalid UTF-8/event envelopes and queue overflow cancel the native session and release it instead of leaving an orphaned receive.

Real tests covered receive pending during send, close during receive, cancellation during connect/receive, remote disconnect, double close, eight parallel sessions, five sequential sessions, and UI heartbeat during a stalled handshake. No deadlock, crash, or use-after-free was observed.

## C. Proxy, PAC, authentication, and TLS

Production uses WinHTTP automatic proxy mode, so Windows system proxy and the WinHTTP PAC/WPAD path are selected by the OS. There is no Dart `DIRECT` fallback when the system transport/DLL fails. Explicit named/direct modes exist only as isolated test controls.

HTTP proxy WebSocket tunnelling was exercised through a local isolated proxy with `CONNECT` followed by upgrade. An unreachable named proxy failed without reaching the target. HTTP 407 was classified as proxy failure. The application permits one integrated-auth retry; Negotiate is preferred over NTLM, both use Windows default credentials, and additional wire exchanges remain bounded by WinHTTP's integrated-auth handshake and request timeouts.

TLS uses the default WinHTTP/Schannel validation and Windows trust stores. No security-ignore flag, `WINHTTP_OPTION_SECURITY_FLAGS`, permissive callback, or certificate bypass exists. A local untrusted certificate was rejected and classified as TLS. Date, hostname, CA, revoked, wrong-usage, secure-channel, and proxy-secure WinHTTP codes have native classification coverage.

Not claimed as live PASS: host system-proxy mutation, live PAC/WPAD discovery, domain Kerberos/NTLM proxy authentication, a trusted enterprise TLS-inspection root, hostname/date failures generated by separate live certificates, and Windows 11. These remain controlled VM/domain-lab gates.

## D. `/ws/bind`

Final Windows route semantics remain:

1. `directOnly && proxyOnly` -> call error.
2. `proxyOnly` -> only owned/ready `127.0.0.1:<mixed-port>` local ZEON proxy, with no system/direct fallback.
3. `directOnly` -> Windows system networking through the WinHTTP WebSocket backend.
4. Control-plane -> existing adaptive policy.
5. Ordinary request -> existing adaptive policy.

`/ws/bind` system-network routing was exercised through `DioHttpClient.openWebSocket` and the production WinHTTP backend. Local ZEON proxy routing retains the Dart WebSocket path because that path intentionally connects through the owned mixed proxy. Missing native DLL remains fail-closed, but CMake now builds and installs the DLL next to `ZEON.exe`, so absence is a packaging failure rather than a normal production state.

The existing bind event protocol/API was not changed. Connect, receive, status-event delivery, normal/remote close, cancellation, and repeated sessions are covered at the route/transport boundary. Idle production-server behavior and full bind confirm/reconnect remain part of fresh-install VM E2E. WinHTTP responds to peer ping control frames internally but exposes no client-ping send API; the existing `setPingInterval` call is therefore non-operative on this backend, while the receive timeout remains bounded. Server idle-policy compatibility must be confirmed in the VM E2E.
