# Аудит RU-сервисов и стабильности VPN (устройство)

Дата: 2026-05-20
Устройство: Samsung SM-S928B (Android 16)
Приложение: ZEON/Hiddify-based APK (после пересборки и установки)

## 1. Что проверено

- Подключение телефона по USB через ADB.
- Подъем VPN-сессии в приложении (с подтверждением системных диалогов).
- Проверка наличия `tun0` и параметров интерфейса.
- Серии HTTPS-проверок для:
  - `https://ya.ru`
  - `https://wildberries.ru`
  - `https://www.ozon.ru`
- Проверки в браузере Chrome (лог `ssl_client_socket_impl ... net_error -100`).
- Сопутствующая проверка ping/базовой сетевой доступности.

## 2. Фактическое состояние VPN

VPN поднят успешно:

- `tun0` присутствует
- IPv4: `172.19.0.1/28`
- IPv6: `fdfe:dcba:9876::1/126`
- MTU: `1500`

Это подтверждает, что проблема не в полном падении VPN-сервиса (не «VPN вообще не работает»), а в избирательном HTTPS/TLS-сценарии.

## 3. Результаты по RU-сервисам

### 3.1 Curl (через телефон при активном VPN)

Наблюдение по сериям запросов:

- `ya.ru`:
  - dual-stack: нестабильно/падает с TLS-ошибками (`curl rc=35`, TLS connect error)
  - IPv4 (`curl -4`): успешно (HTTP-ответы есть)
- `wildberries.ru`:
  - dual-stack: нестабильно/падает с TLS-ошибками (`curl rc=35`)
  - IPv4 (`curl -4`): успешно (HTTP 307)
- `ozon.ru`:
  - dual-stack: успешно (HTTP 307)
  - IPv4 (`curl -4`): успешно (HTTP 307)

Итог: проблема селективная и связана не с DNS-резолвом как таковым, а с HTTPS/TLS-путем для части направлений при участии IPv6/dual-stack.

### 3.2 Браузер Chrome (реальный пользовательский сценарий)

При открытии `ya.ru` и `wildberries.ru` в логах Chromium фиксируется:

- `ssl_client_socket_impl.cc ... handshake failed ... net_error -100`

При открытии `ozon.ru` таких TLS-ошибок не зафиксировано.

Итог по браузеру: симптом подтвержден именно на уровне реального веб-клиента, а не только в curl.

## 4. Стабильность и скорость

- ICMP/ping до RU-доменов проходит стабильно (0% packet loss, низкий RTT).
- Это значит, что базовая IP-связность есть, но HTTPS/TLS ломается точечно.
- Следовательно, «низкая скорость/плохая стабильность» в пользовательском восприятии сейчас в первую очередь вызваны TLS-failure для части популярных RU-сервисов, а не тотальным отсутствием канала.

## 5. Что именно влияет на сбои

Подтвержденные факторы:

1. В активной VPN-сессии участвует IPv6-path (`tun0` имеет IPv6-адрес).
2. Для части RU-доменов (ya/wildberries) dual-stack путь дает TLS handshake failure.
3. Для тех же сервисов IPv4 путь успешен.
4. Ozon проходит и в dual-stack, и в IPv4, то есть проблема избирательна по направлению/маршруту, а не глобальна.

## 6. Ключевой вывод аудита

Корневая эксплуатационная проблема на текущем состоянии сборки:

- selective HTTPS/TLS failure для части RU-сервисов при активном VPN,
- коррелирует с участием IPv6/dual-stack пути,
- при IPv4 путь рабочий.

Это не похоже на простой DNS-отказ, не похоже на «не работает интернет», и не должно лечиться скрытым direct bypass для `ya.ru/wildberries.ru`.

## 7. Логи/индикаторы, подтверждающие вывод

- `ip addr show tun0`:
  - `inet 172.19.0.1/28`
  - `inet6 fdfe:dcba:9876::1/126`
- Chrome logcat:
  - `ssl_client_socket_impl.cc ... handshake failed ... net_error -100` (на ya/wildberries)
- Curl:
  - dual-stack: ошибки TLS на ya/wildberries
  - `-4`: успешные ответы на ya/wildberries/ozon

## 8. Практические рекомендации (без маскировки direct bypass)

1. Привести runtime к строгому соблюдению UI-флага IPv6 (если выключен в UI — IPv6 не должен участвовать в VPN-конфиге).
2. Для стабильного Android-профиля использовать `IPv4-first`/`IPv4-only` режим в VPN-конфиге (без вывода RU-доменов в direct).
3. Синхронизировать DNS/route policy, чтобы не было route-DNS рассинхронизации.
4. Добавить RU HTTPS healthcheck (ya/wildberries/ozon) в логику оценки нод, а не только generic check.
5. Оставить Force VPN semantics: весь трафик через VPN, direct только по явному пользовательскому bypass.

## 9. Статус на конец аудита

- VPN на устройстве поднят и работает как сервис (`tun0` активен).
- Проблема с RU-сервисами воспроизводится селективно (ya/wildberries падают по TLS в dual-stack/браузере).
- Ozon работает.
- Аудит подтверждает: текущая деградация связана с path/TLS-поведением (прежде всего IPv6/dual-stack), а не с полным отказом сервера/канала.
