## Ключевой результат
### P0: VPN в TUN-режиме не поднимается
Повторяемая ошибка при старте:
- `manager start inbound/tun[tun-in]: configure tun interface: permission denied`

Симптомы:
- `tun0` отсутствует (`Device "tun0" does not exist`).
- Статус соединения: `ConnectionFailure.unexpected(...)`.

Вывод:
- На этом коммите основная проблема не «медленный VPN», а **фактический отказ запуска VPN-интерфейса**.
- Пока `tun0` не создается, говорить о стабильной скорости через VPN нельзя.

## Логи (фрагменты)
- `failed to start bg core: ... configure tun interface: permission denied`
- `connection status: CONNECTION FAILURE: ... startService - manager start inbound/tun[tun-in]...`
- `Device "tun0" does not exist`

## Проверка RU-сервисов
### Через VPN
Невалидно для оценки качества VPN, потому что VPN не поднялся (`tun0` отсутствует).

### Без VPN / по системной сети (контроль)
Ping до RU-доменов успешен, без потерь:
- `ya.ru`: 0% loss, avg RTT ~40.4 ms
- `wildberries.ru`: 0% loss, avg RTT ~42.7 ms
- `ozon.ru`: 0% loss, avg RTT ~39.1 ms

Это показывает, что базовый интернет-канал устройства в момент теста работоспособен.

## Почему скорость/стабильность «очень плохие»
На данном коммите первопричина следующая:
1. VPN соединение в TUN-режиме не стартует из-за `permission denied` на этапе конфигурации tun-интерфейса.
2. При отсутствии активного VPN весь трафик VPN-пути отсутствует/рвется на старте, что воспринимается как «очень медленно/не работает».

Итого: деградация вызвана не только качеством серверных нод, а **критическим сбоем поднятия клиентского VPN-интерфейса**.

## Что поломано относительно рабочего сценария
1. Критичный этап `start inbound/tun` завершается ошибкой.
2. Отсутствует `tun0`, следовательно нет полноценного VPN datapath.
3. Нельзя корректно оценить производительность VPN (скорость/latency/jitter) до устранения P0.
